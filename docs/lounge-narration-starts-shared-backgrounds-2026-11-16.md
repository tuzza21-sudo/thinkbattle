# 묘사 표시·첫 대화 장소·공용 배경 — 2026-11-16

요청한 세 변경을 로컬 코드에 반영했다. 운영 DB는 조사용으로 읽었으며 수정하지 않았다. 이미지나 대화를 실제 유료 API로 생성하지 않았다. 아래 SQL 적용과 코드 배포가 남아 있다.

## 묘사는 괄호 없이 기울임체

서버가 `*묘사*`를 `(묘사)`로 다시 바꾸던 처리를 제거했다. 새 응답과 모델이 참고하는 대사 예시는 별표 한 쌍을 묘사 구분자로 사용한다. 화면은 구분자를 숨기고 같은 기울임체로 표시한다.

이전 대화의 괄호 묘사도 화면에서 같은 방식으로 표시한다. 한 줄 전체뿐 아니라 대사 중간·여러 줄·입력 중 아직 닫히지 않은 묘사도 지원한다. 기술 설명인 `HBM(고대역폭 메모리)`와 사용자가 직접 적은 괄호는 보존한다. 저장된 과거 대화를 일괄 수정하지 않는다.

타자 효과의 마지막 글자도 같은 묘사 스타일을 따른다. 속마음은 기존 ‘속마음’ 제목과 독립된 영역을 유지한다. 낭독은 묘사를 읽지 않으며 행동 기록·질문 종료 판정도 새 구분자를 이해한다.

## 프롤로그와 실제 첫 대화 장소를 일치

프롤로그와 실제 첫 대화 장소를 맞춘다. 강무진은 이동을 줄이기 위해 계약 협상 자체를 생략하지 않고 회의실에서 협상을 시작한다.

| 캐릭터 | 새 첫 대화 장소 |
| --- | --- |
| 강무진 | 고층 빌딩 회의실. 여성 의뢰인과 계약 조건을 협상하는 자리 |
| 서도현 | 호텔 라운지 레스토랑의 식사 테이블 |
| 강혜인 | 이미 출발한 산악회 버스 안, 나란히 앉은 뒷자리 |

원인은 ‘10턴이면 강제 이동’하는 규칙이 아니었다. 기존 시작은 사무실·현관 앞 차·버스 계단처럼 곧 이동할 자리였고 프롤로그에 다음 목적지가 예고돼 있었다. 사용자 제작 캐릭터는 시작 장소를 따로 저장할 항목이 없어 `scenario.place`가 빈 문자열이었다. 화면 자동 배경은 엔진이나 요약에 장소가 생긴 뒤에야 결정할 수 있었다.

새 첫 답변은 프롤로그 마지막 장소를 현재 장면으로 전달받는다. 강무진은 가족 식사로 앞당기지 않고 회의실의 계약 협상을 첫 장면으로 유지한다. 여성 의뢰인은 가짜 연인을 원하고, 그는 6개월 동안 실제로 만나 보자는 조건을 역제안한다. 초안·조건 협상·서명은 실제 대화로 진행하며 합의 완료로 미리 처리하지 않는다. 이미 합의한 기존 대화의 계약과 실제 진행은 유지한다.

새 방의 배경도 아직 요약·장면 기록이 없으면 프롤로그의 마지막 장소를 사용한다. 같은 장소의 종류가 나중에 ‘기타’에서 ‘집’으로 정교해진 것을 이동으로 오인하지 않게 키도 정리했다. 이동 경위를 정리할 때 계약 협상 같은 핵심 역할극은 생략하지 않는다.

사용자 제작 캐릭터에 선택 항목 `storyPlace`를 추가했다. AI 프롤로그 생성도 마지막 장소를 함께 쓰고, 제작 화면에서 수정할 수 있다. 방 생성 RPC가 이 값을 보존한다. 강혜인은 확인한 해당 캐릭터 ID만 대상으로 하며 다른 프로필 필드는 유지한다.

기존 대화 이어하기는 장소·기록을 새 프롤로그로 되감지 않는다. 이후 실제 이동이 생기면 기존 장면 진행·배경 자동 전환은 계속 동작한다. 10턴 이동 금지 같은 새 제약은 추가하지 않았다.

## 직접 만든 배경도 공용으로 재사용

기존 자동 장면 배경은 공용 라이브러리를 사용했지만 ‘직접 만들기’는 개인 폴더에만 저장해 검색에서 빠졌다. 이제 이 경로도 공용 라이브러리에 연결한다.

1. 자기 방 소유권을 확인한 뒤 정규화한 요청의 SHA-256 키로 기존 배경을 확인한다. 같은 요청이면 이미지·모델 호출 없이 재사용한다.
2. 요청이 다르면 검색으로 후보를 찾고 기존 배경이 맞는지 판단한다. 맞는 것이 있으면 새 이미지를 생성하지 않는다.
3. 새로 만들어야 하면 공용 장소 설명·이름·태그를 정리해 인물 없는 배경을 만들고 공용 `scenes/` 경로와 라이브러리에 등록한다. 입력 원문 대신 정리된 장소 정보를 저장한다.
4. 방에도 공용 장면 ID를 저장한다. 등록 실패를 공용 저장 성공처럼 반환하지 않는다. 동시 등록의 고유 키 충돌에서는 먼저 등록된 장면을 사용한다.

공용 생성분과 기존 개인 폴더 생성분을 합쳐 기존 일일 생성 한도를 적용한다. 재사용에는 이미지 생성 한도를 소모하지 않는다. 예전 개인 이미지들을 일괄 공개하지 않았다. 만들기 화면에는 공용 재사용 사실을 표시했다.

검색은 이름·태그·설명에 대한 가중 전문 검색과 GIN 인덱스를 사용한다. 한국어 합성 장소명도 분리하며 인기 상위 400장 밖의 배경도 검색 후보가 된다. 사용 횟수는 관련도 뒤의 정렬 기준이다. 선택 화면에도 검색창을 추가했다.

## 검증과 적용

- 19개 회귀 검사 파일: 410개 통과, 실패 0개.
- TypeScript 타입 검사·프로덕션 빌드 통과.
- 실제 메시지 렌더러 SSR: 옛 괄호·새 별표·입력 중 묘사가 같은 기울임체로 표시되고 속마음 영역은 분리됨.
- 이미지 API 핸들러 가상 검사: 사용자 A가 생성·등록한 배경을 사용자 B가 추가 모델·이미지 호출 없이 재사용함.
- 격리 PGlite DB: 인기 배경 450개 뒤의 관련 배경 검색, 태그 변경 후 인덱스 갱신, 한 글자 검색·개수 제한, 새 시작 장소, SQL 중복 적용·진행 중인 방 보존 검사 통과.
- 실제 유료 생성·운영 DB 변경·배포는 실행하지 않음.

다음 순서로 적용한다.

1. `supabase/migrations/20261221000000_lounge_scene_search.sql`: 공용 검색 인덱스·검색 RPC·생성 경로 구분.
2. `supabase/migrations/20261222000000_lounge_arrived_story_starts.sql`: 서도현·강혜인의 시작 장면과 사용자 제작 캐릭터의 시작 장소 저장.
3. `supabase/migrations/20261223000000_lounge_closer_negotiation_start.sql`: 강무진의 회의실 계약 협상 시작. 이전 식사 시작 버전의 SQL을 이미 적용한 DB도 이 파일로 바로잡을 수 있다.
4. 코드 배포. 새 직접 생성 경로를 사용하려면 SQL을 먼저 적용해야 한다. 프롤로그 변경은 새로 시작하는 방에 적용된다.
