# AI 대화 보호와 참가자 질문 연결

2026-10-03 구현. 음성 전사 결과를 서버에서 판정해 경고·일시 발언 제한을 적용하고, 순서 대화 중 특정 참가자에게 한 질문을 답변 차례로 연결한다. 기존 친구 기획과 별개이며 친구 관계를 생성하지 않는다.

## 실제 환경에 적용하기

1. 기존 라운지 마이그레이션을 적용한 Supabase 프로젝트의 SQL Editor에서 [새 마이그레이션](../supabase/migrations/20261003000000_voice_lounge_safety_and_questions.sql) 전체를 실행한다. 마지막 선행 파일은 `20261002040000_voice_lounge_cafe_and_seaside.sql`이다. 재실행도 가능하다.
2. 서버 환경에 `SUPABASE_SERVICE_ROLE_KEY`를 설정한다. 로컬은 `.env.local`, 원격은 배포 환경의 서버 환경변수에 넣는다. `VITE_` 접두사를 붙이거나 브라우저 코드에 넣지 않는다. 기존 `OPENAI_API_KEY`, Supabase URL·공개키, LiveKit URL·관리자 키도 필요하다.
3. 로컬 개발 서버를 재시작한다. 원격 환경은 변경 코드를 배포해야 한다. 이 작업에서는 원격 DB 적용, 키 설정, Git push, 배포를 수행하지 않았다.

현재 로컬 설정에는 `SUPABASE_SERVICE_ROLE_KEY`가 없다. 따라서 기능 코드와 분리된 DB 검증은 완료했지만 실제 방에서 판정 API를 활성화하려면 위 설정이 필요하다. 미설정 API는 `503 / lounge_interaction_not_configured`로 응답한다.

로컬에서 “AI 대화 보호 서버 설정을 확인해 주세요”가 뜨면 Supabase 프로젝트의 Settings → API Keys에서 현재 서버 코드가 사용하는 `service_role` 키를 확인하고 `.env.local`에 `SUPABASE_SERVICE_ROLE_KEY=실제키`로 설정한다. 기존 공개키(`anon`)를 복사하지 않는다. 키는 서버 전용으로 두며 `VITE_` 접두사를 붙이거나 채팅에 공유하지 않는다. [Supabase 공식 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)를 참고한다. 개발 서버를 재시작하고 방 페이지를 새로고침한다. SQL이 미적용이면 위 마이그레이션도 별도로 적용해야 한다.

2026-10-03 로컬 진단: `/api/lounge-interaction`의 실제 503 응답에서 `lounge_interaction_not_configured`, `retryable: false`를 확인했다. 클라이언트가 오류 코드·재시도 여부를 유지하도록 수정했으며, 해당 설정 오류를 받은 방에서는 주기적 동기화와 전사 이후 자동 검토 요청을 멈춘다. 설정 안내는 유지하고 일반 전사·사회자 대화는 계속할 수 있다. 일시적인 502 오류는 자동 재시도를 유지한다. 설정 후 새로고침하면 다시 확인한다. 모의 API 검사 47개와 실제 React 브라우저 검사에서 설정 오류 이후 요청 중단, 전사 유지, 일시 오류의 복구를 확인한다. 실제 보호 기능 활성화는 관리자 키 설정 후 확인해야 한다.

## 대화 보호 규칙

| 판정 | 동작 |
| --- | --- |
| 서로 다른 의견, 인물·작품 비판, 대사 인용, 피해 경험, 모호한 전사 | 제한하지 않음 |
| 실제 상대에게 한 일반적인 인신공격·욕설·괴롭힘 | 1차 경고. 같은 방에서 별도 발언의 2차 위반 시 2분 발언 제한 |
| 수위가 심한 인신공격, 명확한 폭력 위협·혐오 공격·성적 괴롭힘 | 첫 위반에도 경고 없이 즉시 5분 발언 제한 |
| 불확실한 판정·AI 요청 실패 | 자동 제한하지 않음 |

제한 대상은 사람의 성격이나 호감도가 아니라 실제 발언이다. 전사 내용을 함께한 참가자 닉네임, 방 주제, 최근 발언 문맥과 함께 검토한다. 모델의 높은 확신만 적용하며 수위를 `ordinary`·`severe`로 구분한다. 일반 괴롭힘은 모델이 강한 제한을 반환해도 경고 규칙을 따르고, 수위가 심한 공격은 첫 위반에도 제한한다. 욕설 단어가 있다는 이유만으로 심한 공격으로 분류하지 않는다. 이는 코드로 보수적으로 처리하는 규칙이며 실제 음성에서 오판이 없다는 보장은 아니다.

동일한 전사 메시지는 한 번만 처리한다. 같은 공식 차례의 분할 녹음은 경고를 중복 계산하지 않으며, 자유 대화는 30초 안의 경고를 묶는다. 위반으로 판정된 기록은 보호 안내로 대체한다. 제한 중에는 현재 차례를 종료하고 기본·손들기·답변 차례에서 제외한다. 글 발언 저장과 유료 음성 전사 티켓도 서버에서 거절한다.

화면에는 경고 또는 남은 제한 시간을 표시한다. 제한 중에도 다른 참가자의 이야기를 들을 수 있다. 방장은 해당 참가자 프로필의 `발언 제한 해제` 버튼으로 제한과 경고를 초기화할 수 있다. 시간이 지나면 권한이 복구되며 마이크는 이용자가 다시 켠다. 자동 만료 후 경고 이력은 같은 방에서 유지된다.

LiveKit 관리자 API로 음성 게시 권한을 변경하고, 수신 측에서도 제한된 참가자의 트랙을 음소거한다. 방장 브라우저가 5초 간격으로 권한을 확인하므로 재접속 시 오래된 토큰으로 입장한 경우도 다시 반영한다. 이미 들린 음성은 되돌릴 수 없고 전사·판정·권한 동기화만큼 지연될 수 있다. 서버 장애나 방장 브라우저 종료 시 즉시 차단을 보장하지 않는다. LiveKit의 권한 변경 시 기존 트랙이 해제되는 동작과 토큰 재사용 제약은 [참가자 권한 문서](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/), [토큰 문서](https://docs.livekit.io/frontends/reference/tokens-grants/)를 참고한다.

현재 AI 음성은 방장의 LiveKit 참가자로 방송한다. 방장 본인이 제한되면 AI 방송도 일시 중단하며, 게시할 수 없는 AI 음성을 생성하는 요청도 막는다. 자동 사회자 방송을 방장과 독립적으로 유지하려면 별도 서버 참가자로 옮겨야 한다.

## 특정 참가자에게 질문하기

`소연님, 이 책에서 어떤 문장이 가장 마음에 남았어요?`처럼 실제 닉네임을 부르며 한 사람에게 질문한다. 모델이 답변 대상과 질문을 정리한 뒤 서버가 다음 조건을 다시 확인한다.

- 본인·AI·작품 속 인물이 아닌, 현재 참여 중인 제한되지 않은 참가자여야 한다.
- 발언에 닉네임이 실제 포함돼야 하며 동명이인이나 `그분/너/친구/다들`처럼 모호한 대상은 자동 연결하지 않는다.
- 공격적인 질문은 답변을 요청하지 않는다.
- 순서 진행이 적용된 그룹 방에서, 실제 시작된 기본·손들기 차례의 질문만 연결한다. 1:1 AI 대화나 기존 자유 대화방은 해당 답변 차례를 생성하지 않는다.

발언자가 `이야기 마쳤어요` 또는 `패스`를 누르면 마지막 녹음의 전사·저장을 확인한 뒤 차례를 넘긴다. 보호 판정·질문 분석의 완료를 기다리지 않는다. 질문자가 아직 말하는 중에는 차례를 빼앗지 않는다. 질문 분석이 먼저 끝나면 질문자가 마친 뒤 답변 차례를 연결하며, 늦게 도착한 분석은 이미 말하기 시작한 참가자를 중단하지 않고 답변 대기열에 둔다. 분석 결과가 다음 기본 차례의 안내보다 늦으면 특정 참가자의 답변도 이후 차례에 연결될 수 있다.

## 전사 표시를 우선하는 처리

2026-10-03 속도 우선 개편: 전사 저장 성공 직후 기록 갱신을 시작하고, 보호 검토를 별도 비동기 요청으로 진행한다. 두 요청 모두 음성 전사 대기열의 완료 조건에 넣지 않는다. 다음 음성 조각과 발언 종료는 저장까지만 기다린다. 사회자 요청도 보호 검사 완료를 기다리지 않는다. 실제 화면 표시는 저장된 메시지를 다시 읽는 네트워크 시간과 React 갱신이 필요하지만, 보호 모델의 응답 시간은 그 앞에 붙지 않는다.

보호 판단이 완료되면 다시 방 상태를 읽어 1차 경고·2차 제한·심한 발언 즉시 제한의 기존 규칙을 적용한다. 이때 위반 기록을 보호 안내로 바꾸고, 마이크 게시 권한과 참가자 표시를 갱신한다. 검토 전에는 원문이 표시되고 들린 음성은 되돌릴 수 없다. 판단 실패는 보호 오류 안내와 기존 재확인 경로로 처리하며 일반 전사나 다음 발언을 막지 않는다. 판정·중복 경고 방지 SQL과 모델 호출 횟수 구조는 유지한다.

콘솔의 `transcriptionMs`는 음성 전사·저장까지, `interactionMs`는 그 뒤의 보호 검토·결과 갱신까지 따로 기록한다. 보호 결과가 늦게 도착해도 이미 나간 방의 결과를 다른 방 화면에 적용하지 않도록 방 식별자와 마운트 상태를 확인한다.

실제 React 검사에서는 주기적인 기록 갱신을 꺼 두고 보호 요청을 완료시키지 않은 채로 두 발언이 직접 갱신되는지, 전사 대기열과 발언 종료가 완료되는지 확인한다. 이후 보호 응답을 순서대로 완료해 경고·기록 숨김·마이크 제한이 나중에 반영되는지 확인한다. 실제 서버와 네트워크에서의 지연 감소 시간은 별도 측정이 필요하다.

답변 대상은 `말하기` 또는 `패스`를 선택할 수 있다. 답변 후 원래 순서로 돌아가며 기본 발언 기회는 소비하지 않는다. 화면에는 질문 원문 요약, 질문한 사람, 답변 대기 명단을 표시하고 사회자는 그 질문에 답하도록 안내한다. 사회자가 상대 대신 답하지 않도록 프롬프트를 분리했다.

한 원래 차례에서 답변 연결은 한 번만 허용한다. 답변 차례에서 또 답변 차례를 연쇄 생성하지 않으며, 대기 질문은 해당 단계 안에서만 처리한다. 여러 사람의 기본 기회가 질문 하나로 계속 밀리지 않게 하기 위한 규칙이다.

## 서버와 비용

`/api/lounge-interaction`은 로그인과 실제 방 참여를 확인한다. 클라이언트가 보내는 판정·발언 내용·행위자 ID는 사용하지 않고 DB에 저장된 발언과 인증된 사용자만 사용한다. 판정·해제·음성 동기화 RPC는 서버의 `service_role`만 실행할 수 있다. 이용자는 DB 필드를 직접 수정하거나 다른 사람의 제한을 해제할 수 없다.

신규 전사마다 별도의 `gpt-6-luna` Responses 요청으로 보호 판정과 질문 감지를 함께 처리하므로 LLM 비용이 추가된다. 웹 검색이나 TTS는 이 판정 요청에서 하지 않는다. 처리된 발언은 재판정하지 않으며, 실패 재시도는 메시지당 최대 3회다. 엄격한 JSON 스키마와 런타임 검증을 함께 사용한다. [OpenAI Structured Outputs 문서](https://developers.openai.com/api/docs/guides/structured-outputs)를 참고한다.

기존 `estimateLoungeCost`와 1시간 비용표는 사회자·전사·TTS만 계산하므로 이번 판정 요청의 추가 토큰 비용은 포함하지 않는다.

AI 판정을 저장한 뒤 LiveKit 동기화가 실패해도 동일 발언을 다시 경고로 계산하지 않는다. DB에는 적용된 결정을 유지하고 음성 권한 동기화만 재시도한다. 제공자 오류 원문이나 관리자 키는 응답에 포함하지 않는다. Vercel에는 이 API의 `maxDuration: 60`을 설정했다.
