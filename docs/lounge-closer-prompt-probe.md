# 강무진 프롬프트 및 엔진 점검 — 2026-11-05

> 아래 분석·24회 비교는 변경 전 구성에 대한 기록이다. 이후 사용자의 적용 요청에 따라 첨부 패치와 관련 지침을 실제 소스에 반영했다. 최신 적용 범위는 문서 마지막의 「적용 후 변경」을 따른다.

이번 점검의 운영 DB 작업은 요청받은 계정의 강무진·윤지안 기록에 대한 GET뿐이다. 실제 채팅 발송, DB·스키마 변경, 배포, 캐릭터 교체는 하지 않았다. 첨부 `closerPatch`는 테스트 프로세스의 메모리에서만 병합했다. 기존 작업 트리의 수정은 보존했다.

## 1. 3인칭 퓨샷이 적용되지 않는가?

아니다. `src/lib/loungeCharacters.ts`의 `loungeFewShotTurn`은 예시의 `reply`를 JSON의 `text`로 그대로 옮긴다. 3인칭 필터나 괄호 행동으로 바꾸는 변환이 없다. `loungeCompanionSheetPrompt`는 `bible.fewShot` 전체를 배열 순서대로 직렬화한다.

현재 강무진의 **21개가 모두** 포함된다. 순서는 A 기싸움 3개 → B 식사·이동 3개 → C 호감 3개 → D 지적·화해 3개 → E 업무 3개 → F 신뢰 3개 → G 계약연애 3개다. 단계나 현재 장면에 따른 사전 선택은 없다. 첫 단계에도 이후 단계 14개가 들어가며, 자연어로만 “높은 단계의 행동은 아직 하지 않는다”고 지시한다.

예시의 첫 답은 `무진이 … 웃는다`, `그가 … 기대앉는다`, 따옴표 대사를 그대로 포함한다. 반면 활성 채팅 지침은 **따옴표 없는 대사 + 필요할 때 괄호 행동**, **3인칭 서술 금지**다. 예시가 무시되는 문제가 아니라 서로 다른 형식을 학습시키는 충돌이다.

`cleanLoungeCompanionReply`도 3인칭을 자동으로 고치지 않는다. 직접 검사한 `강무진은 당신을 바라봤다.`는 그대로 남고 `third_person` 메모만 붙는다. 별표 행동 제거·괄호 행동 수 제한과 구별해야 한다.

## 2. 활성 요청의 조립 순서와 문체

주요 경로는 `api/lounge.ts`의 `messenger` 분기다.

1. `loungePersonaPrompt(..., {withBible:true})`: 이름·직업·태그라인·과거·습관. 이 경로에서는 `personality` 배열을 중복 방지 목적으로 생략한다.
2. 공통 캐릭터 응답 원칙과 `loungeContinuityRule`.
3. 관계 공통 지침: reserve 우선, speech_level, 친밀도 등.
4. `loungeBiblePrompt`: voice.tone, 욕망·두려움·겉/속·유머·반응·불변·성장.
5. `loungeCompanionSheetPrompt`: 분량·rhythm·행동·속마음·예시 전체.
6. `loungeCompanionRules`: 출력 형식, 장면, 반응, 사용자 행동을 대신 쓰지 않는 원칙 등.
7. 별도 JSON input: scenario, 관계 단계와 점수, memory, 최근 대화, turn, 사용 가능한 analyzer/director 결과 등.

DeepSeek에서는 조립한 instructions가 system, JSON input이 user 메시지로 간다. voice.tone과 공통 지침은 같은 system 내용에 포함되므로 서로 다른 API 역할의 우선순위라고 표현하면 부정확하다. 다만 공통 지침은 “다른 규칙보다 먼저”, “모든 문장”처럼 명시적인 우선·강제 표현을 쓴다.

소설처럼 생생하게 쓰거나 별표 지문을 거의 매번 요구하는 기존 문자열도 `api/lounge.ts`에 남아 있다. **이번 활성 companion 요청에는 그 문자열이 포함되지 않음**을 캡처에서 확인했다. 검색 결과에 문자열이 존재한다는 이유만으로 활성 지침으로 보고하지 않는다.

## 4. 계약 사실은 매 턴 들어가는가?

유효한 방 시나리오가 있으면 `normalizeLoungeRoomScenario` → `modelScenario` → `context.scenario`로 매 턴 전달한다. companion 모드에서도 프롤로그가 포함된다. 합성 요청 24개 모두 이를 검증했다. 프롤로그 한도는 12,000자이고 이번 실제 저장본은 그보다 짧다.

그러나 **전달과 준수는 다르다**. 실제 저장된 프롤로그에는 6개월 기간, 가족 앞에서만 연인인 척하는 관계가 아니라는 말, 사생활 공개 금지·평판 보호·종료 후 비밀 유지가 있다. 동시에 가짜 연인 연습, 감정은 약속하지 않았다는 연출도 있다. “성실한 실제 데이트 참여”와 “사랑이라는 감정의 강요”를 구별해 명시할 필요가 있다.

이번 합성 fixture는 사용자의 최신 의도를 명확히 적은 짧은 계약 canon이다. 운영 저장본의 긴 프롤로그와 같지 않다. 따라서 합성 결과가 좋아도 기존 방에서 같은 결과가 보장된다고 주장할 수 없다.

기간·잔여 개월·외부인의 지식·현재 말투를 검증하는 구조화된 계약 상태는 이번 경로에 없다. 최근 강무진 방의 story_state도 null이다. 핵심 사실은 프롤로그와 텍스트 요약에 의존한다.

## 5. 안전·품질 규칙이 도발과 연애를 전부 순화하는가?

**일괄적인 의미 재작성 필터는 확인되지 않았다.** closer는 adultFlirtation=true여서 기본적인 연애 금지 문장을 허용 지침으로 치환한다. 일반 플러팅은 가능하다. 별도 성인 모드 allowlist와는 다른 설정이다.

응답 후에는 JSON 파싱, 형식 정리, 속마음 중복·길이 정리 등이 있고, 다른 언어로 답하면 한국어 재요청을 할 수 있다. 빈 응답·실패 시 같은 인물로 답하게 하는 재시도도 존재한다. 모든 도발을 상담체로 다시 쓰는 후처리는 찾지 못했다. 실제 외부 제공자의 필터 적용 여부는 당시 원본 응답 로그 없이 단정할 수 없다.

무난함을 만드는 **코드에서 확인되는 강한 후보**는 first-stage reserve와 outing, 현재 closer stageRomance, 말투 강제다. 사용자 거절·강압 방지 원칙은 유지하면서 이 충돌을 해결해야 한다.

## 6. 첨부 패치 비교 실험

비교안:

- A: 현재 21개 + 현재 바이블.
- B: 첨부 부분 패치를 병합한 6개. 기존 비밀 유지·사실 확인·현실 관계 제한은 유지.
- C: B에서 현재 단계에 맞는 예시를 골라 2~4개. 후기 단계 예시를 억지로 초기 단계로 재분류하지 않음.

장면: 도발, 둘만의 데이트, 업무 판단, 가족의 계약 공개 요구, 2개월 경과 후 남은 기간, 반말 합의 유지, 서운함 수습, 접촉 거절. selection은 이 실험의 명시적인 scene fixture에 따른 것으로, 운영용 범용 장면 분류기를 구현한 것이 아니다.

| 초기 도발 fixture | 퓨샷 | instructions 문자 수 | JSON input 문자 수 |
|---|---:|---:|---:|
| A | 21 | 23,371 | 3,981 |
| B | 6 | 19,603 | 3,981 |
| C | 2 | 18,738 | 3,981 |

이 표는 **문자 수이며 토큰 수가 아니다**. 실제 운영 요청의 전체 길이도 아니다. A→B는 바이블 내용도 바뀌므로 절감과 행동 차이를 전부 퓨샷 개수 탓으로 돌릴 수 없다. B→C가 예시 선택의 비교다. 제공자가 반환한 실측 토큰은 다음 절에 별도로 적었다.

공통 2~3개+장면 1~2개라는 제안은 타당한 실험 방향이다. 다만 첨부 6개 중 초기 단계 예시는 두 개뿐이고 그 둘 모두 계약연애 장면이다. 매번 3~5개라는 수를 맞추기 위해 후기 단계나 무관한 도발 예시를 넣어서는 안 된다. 일반 말투·업무·수습의 짧은 공통 예시와 계약 전용 예시를 구별하고, 단계·시나리오·최신 사용자 의도에 맞게 고르는 비교가 필요하다.

선택된 예시를 캐시 가능한 고정 프롬프트 중간에 갈아 끼우면 그 뒤의 긴 공통 지침까지 캐시 재사용에 불리해질 수 있다. 운영 적용 시 고정 core와 출력 규칙을 먼저 두고, 선택 예시는 뒤쪽에 배치하는 방안도 함께 측정해야 한다. 선택 자체에 새 LLM 호출은 필수가 아니며 기존 analyzer 결과와 현재 장면·단계를 재사용할 수 있다.

첨부 패치의 주석 “계약연애 활성화된 경우 적용”은 JavaScript 주석일 뿐이다. 현재 serializer는 이를 읽거나 계약 예시를 조건부로 거르지 않는다. desire·tagline도 6개월 관계를 전제로 하므로, 일반 강무진 대화에 계약 설정을 주입하지 않도록 별도 검토가 필요하다.

## 재현과 다음 확인

`scripts/lounge-closer-prompt-probe.mjs`를 추가했다. 기본 캡처에서 DB/auth/후처리 쓰기는 모두 가짜 호스트에 응답하며 실제 fetch를 통과시키지 않는다. 첨부 파일은 AST로 리터럴만 읽고 실행하지 않는다. `--recent`만 지정하면 위에서 승인된 계정의 최근 기록을 GET으로 읽고 파일로 저장하지 않는다.

```powershell
node --preserve-symlinks --preserve-symlinks-main scripts/lounge-closer-prompt-probe.mjs '--patch=<첨부 Pasted text.txt 절대경로>' --dry
```

`--dry` 없이 실행하면 실제 합성 모델 비교를 수행한다. 이번 24회는 사용자 전송 승인 후 실행했다. `--out`은 합성 테스트 결과만 저장한다. 실회원 대화·계정 데이터는 모델 비교에 사용하지 않는다. 현재 캐릭터와 엔진은 이번 점검에서 교체하지 않았다.

| B 첨부 6개 | 8 | 15,043.50 | 140.88 | 12,384 | 2.12초 |
| C 장면별 2~4개 | 8 | 14,519.75 | 142.25 | 10,176 | 1.88초 |

총 입력 **377,062**, 출력 **3,408**, 캐시 적중 입력 **297,344**토큰이다. A→B의 평균 입력은 약 14.4% 감소했지만 바이블 문구 변경도 포함한다. 예시 선택만 달라진 B→C는 평균 **523.75토큰, 약 3.5%** 감소다. 짧은 합성 시나리오로 측정한 실제 API usage이며, 실제 회원 방의 비용·요청 크기를 대신하지 않는다.

순서가 A→B→C로 고정되고 장면마다 선택 예시가 바뀌므로 캐시 적중과 지연 시간에 순서·워밍 효과가 있다. C의 총 입력 감소만 보고 실제 청구 비용이나 지연이 같은 비율로 감소한다고 결론 내리지 않는다. 여기서 시간은 비스트리밍 응답 수집 시간이며 앱의 첫 토큰 지연·전체 턴 지연이 아니다.

이 실험에서는 **3인칭 소설체가 24개 모두에서 나오지 않았다**. 현재 21개가 3인칭이어도 모델이 공통 형식 지침을 따를 수 있다는 관측이다. 따라서 “3인칭이라 예시가 적용되지 않는다”거나 “3인칭 예시가 반드시 출력 붕괴를 일으킨다”는 주장은 성립하지 않는다. 충돌을 없애는 정리는 유효하지만 이것만 원인으로 확정할 수 없다.

코드 검사기 플래그는 모두 비었으나 형식의 모든 요구를 통과했다는 뜻은 아니다. 괄호 행동을 대사와 같은 줄에 둔 답이 있고, B·C에서 각 2개씩 **총 4개 응답은 필수 inner_voice 키를 생략**했다. DeepSeek는 JSON 모드이며 코드가 스키마를 system에 설명할 뿐 제공자가 스키마를 강제하지 않으므로, 유효 JSON과 스키마 준수는 다르다. 실제 앱은 속마음이 없으면 빈 값으로 처리할 수 있다.

반말 사례에서는 입력이 polite인 코드 충돌이 있어도 모델은 최근 합의를 따라 반말을 했다. 그러므로 “항상 존댓말로 되돌아온다”는 실제 결과는 이번에 재현되지 않았다. 다만 사용자에게 존재하지 않는 존댓말을 지적한 사례가 두 안에 있었고, 입력의 불일치는 여전히 고쳐야 할 문제다.

### 이 결과로 정한 판단

1. **퓨샷 축소만으로 원하는 캐릭터가 복구됐다고 볼 수 없다.** 세 안 모두 핵심 도발을 업무 협상으로 돌렸다. 공통 관계·말투 제한과 기존 closer 관계 지침의 충돌을 먼저 정리해야 한다. 이것은 코드와 응답이 함께 가리키는 우선순위이며, 개별 지침의 인과를 분리한 실험까지 한 것은 아니다.
2. **6개보다 선택안이 일괄적으로 낫다는 근거도 없다.** C는 사적인 식사 제안은 자연스러웠지만 비밀 유지와 사실 보존에서 문제가 남았다. 이번 selector를 그대로 운영에 적용하지 않는다.
3. **짧고 명확한 canon은 세 안 모두에서 기간·데이트 참여를 전달했다.** 다만 과거 대화가 누적된 실제 방이나 요약 갱신은 검사하지 않았으므로 장기 기억 문제가 해결됐다는 뜻은 아니다.
4. 먼저 계약 유효 상태·성실한 데이트 참여·비밀 유지·확인된 경과를 짧은 현재 사실로 고정하고, 이미 합의한 관계와 감정 공개 한도를 구별한다. 합의된 말투도 응답과 director가 같은 값으로 읽게 한다.
5. 그다음 공통 예시 2개와 상황 예시 1~2개를 **단계·시나리오·최신 의도에 맞게** 고르는 운영 selector를 검토한다. 이번 6개는 공통·계약·수습 예시 구성이 충분히 분리돼 있지 않으므로, 단순 개수 제한을 최종안으로 삼지 않는다.

합성 원문 응답과 usage는 로컬 임시 파일 `%TEMP%/lounge-closer-prompt-probe.json`에 있다. 실제 회원 대화는 그 파일에 포함되지 않는다. 운영 코드·DB·시나리오는 이번 승인된 비교에서도 변경하지 않았다.

## 8. 적용 후 변경

사용자의 후속 요청으로 첨부 `closerPatch`를 `src/lib/loungeCharacters.ts`의 실제 강무진 데이터에 반영했다. quote, tagline, personality, habits와 bible의 명시된 필드를 교체했다. **15개 항목의 값이 첨부와 일치하며 예시 6개 전부가 실제 Companion Sheet에 들어감**을 로컬에서 확인했다. 비밀 유지·문서 비공개·확인된 사실과 경과 보존에 관한 불변 원칙 3개는 추가로 유지·보완했다. 기존 직업·과거·이미지·이벤트 점수는 보존했다.

함께 맞춘 부분은 다음과 같다.

- `configs/closer.ts`: 자신감 있는 반격, 적극적인 호감과 데이트 제안에 맞춰 core·첫 단계 reserve·단계 안내·romance·과거 공개·응답 힌트를 정합화했다. 단계 ID·점수·상승 기준은 그대로다.
- `loungeScenarios.ts` 및 `api/lounge.ts`: closer의 `closer-contract-love`에서만 계약이 유효한 동안 평범한 데이트를 낮은 단계라는 이유로 일괄 거절하지 않는 outing을 전달한다. 응답과 director가 같은 값을 사용한다. 다른 캐릭터·다른 이야기의 outing과 스킨십 한도는 바꾸지 않는다. 명시적인 계약 종료·합의 변경은 현재 기록을 따르도록 한다.
- 공통 관계·채팅·director 지침: speech_level을 최초 기본값으로 정의하고, 이미 서로 합의한 말투는 유지하도록 정리했다. 이미 합의된 연인 관계를 새 고백의 단계 제한으로 취소하지 않게 했다. 이는 프롬프트 및 기존 요약에 기반한 개선이며, 새로운 구조화 말투 저장 필드를 추가한 것은 아니다.
- 대화 요약 지침: 말투 합의를 보존하고, 비밀을 감추기 위한 즉석 설명을 실제 계약·직업·과거로 저장하지 않게 했다.
- 대체 companion과 프로필 소개도 새 캐릭터 방향으로 맞췄다. 별도의 퓨샷 선택기는 적용하지 않았으며 첨부 예시 6개를 사용한다.

변경된 요청 조립과 캐릭터 데이터는 로컬 자동 검사로 확인한다. 앞 절의 24회 모델 응답은 **적용 전 비교 결과**이며, 이 변경본에 대한 재측정으로 표시하지 않는다. 이번 적용에서 유료 모델 호출을 추가하거나 DB·배포를 실행하지 않았다.

적용 후 검증: `test:lounge` 전체 **280/280 통과**, 앱 및 API TypeScript 검사 통과, 이번에 검사한 캐릭터·관계·장면 모듈과 테스트/진단 스크립트 ESLint 통과, `git diff --check` 통과. 첫 단계의 선제적 플러팅을 모든 인물에게 금지하던 기존 테스트는 강무진의 새 의도에 맞게 한정하여 갱신했으며, 다른 캐릭터의 기준은 유지했다.
