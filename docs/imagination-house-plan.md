# 상상의 집 개편 계획

2026-10-08 작성. 지시서 「상상의 집 서비스 전면 개편」의 PART 0~2(제품 철학, 대화방 개설 시스템 전환)를 바탕으로 기존 라운지를 분석하고 단계별 계획을 세운다. 지시서의 나머지 파트(가상 정체성, 실시간 주제, AI 개입 정책, 사용자 연결, 관계·기억, 코인)를 받으면 해당 단계를 상세화한다.

## 1. 바꾸려는 것

| | 지금 (대화 라운지) | 개편 (상상의 집) |
| --- | --- | --- |
| 시작 | 방 개설 → 제목·주제 작성 → 방장 대기 → 사람 모집 → 그룹 대화 | 상상의 집 입장 → 캐릭터/공간 선택 → **즉시 대화** → 다른 사람 합류 → 자연스러운 그룹 대화 |
| 방 | 사용자가 매번 만든다. 최대 1~2시간 뒤 사라진다 | **공간은 항상 있다.** 이름은 고정, 지금 나누는 주제만 바뀐다 |
| 호스트 | 방을 만든 사람(방장). 나가면 방이 끝난다 | **AI 캐릭터가 공간의 호스트.** 첫 입장자는 방장이 아니라 첫 방문객 |
| 인원 | 만들 때 1:1(1명) 또는 그룹(2~6명)으로 고정 | 혼자 들어오면 AI와 1:1, 사람이 들어오면 그룹으로 **자동 전환** |
| 브랜드 | 대화 라운지 | 상상의 집 · "당신은 여기서 누구이고 싶습니까?" |

## 2. 지금 구조에서 방장에 기대는 곳

| 위치 | 방장이 하는 일 | 개편 후 |
| --- | --- | --- |
| `claim_voice_lounge_host` (SQL) | AI 발언 차례를 방장만 받는다 (`r.host_id = auth.uid()`) | 공간의 **방송 담당**(아래 3-B)이 받는다 |
| `useLoungeAudio.playHostStream` | 방장 브라우저가 AI 음성을 `ai-host` 트랙으로 LiveKit에 내보낸다 | 방송 담당이 내보낸다. 사용자에게는 보이지 않는 내부 역할 |
| `useLoungeAudio` 수신부 | `participant.identity === hostId`인 비마이크 트랙을 AI 음성으로 판단 | **트랙 이름 `ai-host`**로 판단 (누가 내보내든 같은 처리) |
| `LoungePage` 방장 루프 | AI 호출 타이밍, 순서 진행 `tick`, 대화 보호 동기화를 방장 브라우저가 돌린다 | 방송 담당 브라우저가 돌린다 |
| `control_voice_lounge('leave')` | 방장이 나가면 방이 끝난다 | 누가 나가도 공간은 남는다. 마지막 사람이 나가면 그 테이블만 정리 |
| `control_voice_lounge('start')` | 방장이 시작 버튼을 누른다 | 시작 버튼 없음. 들어오면 바로 대화 |
| `api/lounge.ts` 관계·기억 | `capacity === 1 && host_id === user`일 때만 관계를 쌓는다. 지난 대화도 `host_id` 기준으로 찾는다 | 사용자·캐릭터 기준으로 바꾼다 (지시서 관계·기억 파트에서 확정) |
| `api/lounge.ts` 역할 지시 | `capacity === 1`이면 1:1 대화 상대, 아니면 그룹 도우미 | **지금 있는 사람 수**로 정한다 |
| 순서 발언(`voice_lounge_sessions`) | 그룹이 동시에 시작한다는 전제의 30분 단계 진행 | 들고 나는 공간과 맞지 않는다. 공간에서는 쓰지 않는다 (코드는 당분간 유지) |

## 3. 핵심 설계 결정 (제안)

### A. 공간과 테이블

- **공간(space)**: 고정된 이름·캐릭터·풍경을 가진 장소. 처음에는 캐릭터 6명에게 하나씩, 인물 소개의 `place`를 그대로 쓴다.

| 공간 (이름은 제안) | 호스트 | 풍경 |
| --- | --- | --- |
| 호텔 라운지 | 윤태오 · 유쾌한 재담꾼 | hotel |
| 바다 테라스 서점 | 한이나 · 다정한 등대지기 | seaside |
| 숲속 서재 | 고민석 · 냉정한 검증가 | forest |
| 루프탑 라운지 | 강무진 · 노련한 협상가 | rooftop |
| 호텔 바 끝자리 | 선우령 · 벨벳 나이프 | hotel |
| 비 오는 창가 카페 | 백도하 · 능청스러운 트릭스터 | cafe |

- **테이블(instance)**: 한 공간 안의 실제 대화 묶음. 기존 `voice_lounge_rooms` 한 행이 테이블 하나다. 사용자에게는 "호텔 바 · 2번 테이블"처럼 보인다.
- **입장 규칙**: 공간에 들어오면 서버가 테이블을 고른다. **사람이 있고 자리가 남은 테이블을 먼저** 고르고(사람끼리 만나게 하는 것이 목적), 없으면 새 테이블을 연다. 테이블 정원은 사람 6명(+AI).
- **정리**: 마지막 사람이 나가거나 모두 오래 비활성이면 그 테이블만 끝난다. 공간은 남는다. 고정 2시간 만료는 쓰지 않는다.

### B. AI 음성을 누가 내보내나

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **방송 담당 (추천, 1단계)** | 지금의 브라우저 음성 파이프라인(스트리밍, 끊김 복구, 음량 보정)을 그대로 쓴다. 새 서버가 필요 없다 | 담당자 브라우저가 백그라운드로 가면 잠깐 끊긴다. 서버가 담당을 넘겨야 한다 |
| 서버 에이전트 (2단계 후보) | 어떤 사용자 브라우저에도 기대지 않는다. 가장 안정적이다 | 상시 실행되는 별도 서버(LiveKit Agents 등)가 필요하다. Vercel 함수로는 안 된다 |

방송 담당은 사용자에게 보이지 않는 내부 역할이다. 테이블에 `broadcaster_id`와 갱신 시각을 두고, 담당자가 몇 초마다 갱신한다. 갱신이 끊기면 서버가 다음 활성 참가자에게 넘긴다(입장 순서). 담당자만 AI 차례를 받고 음성을 내보낸다. 지시서의 "첫 입장자에게 방장 역할을 부여하지 않는다"는 사용자에게 보이는 권한과 책임이 없다는 뜻으로 해석했다. 이 해석이 맞는지 확인이 필요하다.

### C. 혼자 ↔ 여럿 전환

AI의 역할을 방을 만들 때의 정원이 아니라 **지금 연결된 사람 수**로 정한다.
- 1명: 지금의 1:1 대화 상대 방식(매 발언에 바로 응답).
- 2명 이상: 지금의 그룹 도우미 방식(사람끼리 대화하게 두고, 부르거나 긴 침묵일 때만).
- 누가 들어오면 AI가 짧게 맞이하고 지금 이야기를 한 줄로 이어 준다. 정확한 개입 규칙은 지시서의 AI 개입 정책 파트에서 확정한다.

### D. 그대로 쓰는 것

- 음성: LiveKit 연결, 녹음·전사(지연 대비 2중 요청), AI 음성 스트리밍, 캐릭터별 음량 보정.
- AI: 캐릭터 6명의 말투·지시문, 관계 엔진(단계, 지표, 이벤트), 장기 기억, 대화 보호(인신공격 감지·발언 제한).
- 화면: 대화방 레이아웃(풍경, 프로필, 말풍선), 인물 소개 페이지, 프로필 아바타.
- 계정: 로그인, 게스트, 프로필.

## 5. 1단계 구현 (2026-10-09)

> 같은 날 6장에서 바뀌었다: 자동 테이블 배정과 합류 제안은 없애고 사용자가 테이블을 보고 고른다(꽉 차면 대기 또는 새 테이블). 관계는 그룹에서도 쌓인다. 아래의 방장 제거, 방송 담당, 주제, 1:1↔그룹 전환은 그대로다.

**확정한 결정**: 공간은 캐릭터 1명당 1개. 혼자 와도 대화한다. 2명부터는 기존 그룹 규칙(AI 개입 최소화)을 그대로 쓴다. 방장과 방장의 주제 개설은 없다. 주제는 테이블의 누구나 정하거나 바꾼다(캐릭터의 추천에서 고르거나 직접 입력). 관계와 기억은 기존 규칙 그대로(혼자 캐릭터와 이야기할 때만 쌓임). 캐릭터와 장소는 나중에 바뀔 수 있으므로 공간 ID는 장소 기준이다.

**화면**
- `/lounge`: 상상의 집 홈. 브랜드 문구와 공간 6개(풍경, 이름, 주인 캐릭터, 지금 이야기 중인 인원, `들어가기`, `인물 소개`). 방 만들기 화면과 열린 방 목록은 없앴다.
- `/lounge/spaces/:spaceId`: 입장. 이름이 없으면 게스트 또는 로그인을 고르고, 서버가 테이블을 배정해 `/lounge/:roomId`로 연다.
- 대화 화면(공간 테이블): 제목은 공간 이름(두 번째 테이블부터 `· 2번 테이블`), 시작 버튼 없음, 나가도 다른 사람의 대화는 계속. `나누는 이야기` 아래 **주제 패널**: `캐릭터에게 추천받기`(추천 3개가 모두에게 보임) / `직접 정하기`. 주제가 정해지면 한 줄로 접히고 누가 정했는지 보여 준다. 주제를 정하면 캐릭터가 그 주제로 말을 건넨다(혼자면 바로, 여럿이면 대화가 멈출 때). 순서 발언 안내는 공간에서 쓰지 않는다.
- 인물 소개의 버튼은 그 캐릭터의 공간으로 들어간다.

**데이터와 서버** (`20261009000000_voice_lounge_imagination_house_spaces.sql`)
- `voice_lounge_spaces` 6행(장소 ID, 이름, 캐릭터, 풍경, 정원 6). 행을 고치면 이후 열리는 테이블에 반영되고, SQL을 다시 실행해도 덮어쓰지 않는다.
- 테이블은 기존 `voice_lounge_rooms` 행에 `space_id`·`table_no`를 둔다. 입장 시 같은 공간의 내 테이블 → 사람이 가장 많은 빈자리 있는 테이블 → 새 테이블 순으로 배정한다. 10분간 아무도 없던 테이블은 닫히고, 마지막 사람이 나가면 바로 닫힌다. 만료는 사람이 있는 동안 30분씩 연장된다.
- 방송 담당: 각 참가자 브라우저가 4초마다 확인하고, 담당자가 12초 응답이 없거나 나가거나 발언 제한이면 다음 사람이 이어받는다. 담당자만 AI 차례를 받고 AI 음성을 내보내며, 다른 사람 발언의 대화 보호 검토도 맡는다(예전 방장 역할). 화면에는 보이지 않는다.
- 1:1 판단: 테이블에 3분 안에 보인 사람이 1명이면 1:1. 서버(SQL·API)와 화면이 같은 기준을 쓴다. 관계·기억 저장도 이 조건에서만 된다.
- 주제: `set_voice_lounge_topic`(1~80자, 5초 간격, 추천 주제를 고를 때는 실제 추천 목록에 있어야 함), 추천은 `claim/finish_voice_lounge_topic_suggestions`(테이블당 20초에 한 번, `/api/lounge`의 `topics`가 모델로 생성).
- 기존에 만들어진 방(`space_id`가 없는 방)은 방장·순서 발언·만료 등 모든 기존 규칙을 그대로 따른다. 기존 SQL 검사 6개가 바뀐 함수로 모두 통과한다.

**적용 순서**: SQL Editor에서 `20261009000000_voice_lounge_imagination_house_spaces.sql`을 실행한 뒤 클라이언트·API를 배포한다. 원격 DB에는 아직 실행하지 않았다.

**검증**: `scripts/lounge-spaces-sql-check.mjs`(격리 PostgreSQL: 공간 목록, 즉시 시작, 혼자일 때 1:1 응답·관계·기억 저장, 합류 시 같은 테이블과 그룹 규칙, 방송 담당 인계와 발언 제한자 제외, 퇴장과 마지막 퇴장 종료, 정원 초과 시 2번 테이블, 복귀, 다른 공간 이동, 10분 정리, 만료 연장, 주제 설정·추천·권한, 기존 방 규칙 유지, 재실행), `scripts/lounge-spaces.test.mjs`(1:1 판단, 추천 검증), 기존 라운지 테스트·SQL 검사, 빌드. 홈과 주제 패널은 실제 컴포넌트를 모의 데이터로 데스크톱·390px에서 확인했다. 실제 두 사람 이상이 음성으로 들어와 방송 담당이 넘어가는 흐름은 배포 후 확인이 필요하다.

**알려진 한계**
- 방송 담당의 휴대폰이 백그라운드로 가면 담당이 넘어가기까지 최대 약 12초 AI 음성이 멈출 수 있다. 서버 에이전트(3-B)로 옮기면 사라진다.
- 테이블 행의 `host_id`는 테이블을 처음 연 사람으로 남는다(DB 제약과 지난 1:1 대화 요약 조회용). 권한에는 쓰지 않는다.
- `/lounge/about`(서비스 소개)과 `/lounge/preview`는 예전 라운지 기준 화면이다. 브라우저 수동 검사 스크립트(`scripts/lounge-*-browser-check.mjs`)도 예전 방 만들기 흐름을 전제로 한다.

## 6. 솔로 플레이·소셜 모드, 고르는 입장, 그룹 관계 (2026-10-09)

**확정한 결정**
- AI 개입 정책과 사용자 연결은 기존 그대로 쓴다. 코인은 나중에 붙인다.
- 서비스는 **소셜 모드**(캐릭터의 공간에서 여러 사람과)와 **솔로 플레이**(캐릭터와 1:1)로 구성한다. 홈 위쪽에서 고른다(`/lounge`, `/lounge?mode=solo`).
- **1공간 = 1캐릭터.** 테이블은 기본 하나다. 사용자는 아무 테이블에 자동 배정되지 않고, 공간의 **지금 이야기(주제)와 함께 있는 사람**을 보고 참석할지 정한다.
- 자리가 꽉 차면 **대기**(순서대로, 자리가 나면 자동으로 앉음) 또는 **새 테이블 열기** 중에 사용자가 고른다.
- **소셜에서도 관계가 쌓인다.** 다른 사람이 있는 자리에서는 누구의 지난 이야기도 꺼내지 않는다. 단둘이 있거나 본인이 캐릭터를 불러 물을 때만 말한다.

**화면**
- 홈(소셜): 공간 카드마다 상태(아무도 없음 / N명 · 자리 있음 / 가득 참 · N명 대기), 지금 이야기, 참가자 닉네임, 테이블이 여럿이면 그 수. `둘러보고 참석하기`로 공간 페이지에 간다.
- 홈(솔로): 캐릭터 카드(기본형·도전형), `둘이서 시작하기`.
- 공간 페이지 `/lounge/spaces/:id`: 테이블마다 지금 이야기, 참가자, 인원과 `참석하기`. 아무도 없으면 `참석하기`로 첫 테이블을 연다. 모든 테이블이 차면 `자리가 나면 들어가기`와 `새 테이블 열기`를 고른다. 아래에 솔로 플레이.
- **대기 유지**: 대기를 누르면 상상의 집 안의 어느 화면으로 가도, 새로고침해도(30분까지) 대기가 이어진다. 모든 라운지 화면의 대기 확인기가 4초마다 순서를 확인하고 아래쪽 배너(`기다리는 중 · 내 앞에 N명 · 보기 · 취소`)로 보여 준다. 자리가 나면 자동으로 참석한다. 다른 대화방에서 이야기하는 중이면 끌어내지 않고 `자리가 났어요 · 지금 들어가기`를 띄운다. 대기는 한 번에 한 공간이다.
- 입장 경로: `/lounge/spaces/:id/join?table=…`(고른 테이블), `/open`(첫 테이블 또는 모두 찼을 때 새 테이블), `/solo`.

**자리 규칙 (서버)**
- 정원 6명은 공간 단위 잠금 안에서 센다.
- 새 테이블은 빈자리가 있는 테이블이 없을 때만 열린다(`open_voice_lounge_table`).
- 대기는 선착순이다(`voice_lounge_waitlist`). 90초 넘게 확인하지 않은 대기자(상상의 집을 완전히 떠난 사람)는 순서를 잃는다. 백그라운드 탭은 확인이 느려지므로 여유를 둔 값이다. 자리가 나면 앞선 대기자가 먼저 앉고, 대기하지 않은 사람이 그 자리를 가져갈 수 없다(`enter_voice_lounge_table`). 앉거나 새 테이블을 열면 대기에서 빠진다.
- 솔로 플레이는 기존 1:1 방이다. 같은 캐릭터와 끝나지 않은 1:1이 있으면 이어서 하고, 공간 인원에 세지 않는다.

**그룹에서의 관계와 기억**
| 상황 | 동작 |
| --- | --- |
| 솔로 플레이 | 기존 그대로. 매 발언에 관계가 쌓이고, 장기 기억을 **기록**하고 꺼낸다. 장기 기억은 여기서만 기록한다 |
| 공간에서 혼자 | 관계가 쌓이고, 솔로 플레이에서 쌓인 기억을 꺼내 쓴다. 새로 기록하지는 않는다 |
| 여럿이, 누군가 말할 때 | 이미 하던 발언별 대화 보호 검토 호출에서 그 사람의 행동(관계 이벤트)을 함께 분류해 그 사람의 관계에 반영한다. 추가 AI 호출은 없다. 장기 기억은 기록하지 않는다 |
| 여럿이, 캐릭터가 말할 때 | 참가자별 관계 단계를 그 사람을 대하는 말투·온도에만 반영한다. 누구의 지난 대화·기억도 먼저 꺼내지 않는다 |
| 여럿이, 누군가 캐릭터를 불러 자기 얘기를 물을 때 | 그 사람 본인의 기억만, 다른 사람 앞에서 말해도 되는 범위에서 짧게 답한다. 민감하면 둘이 있을 때 이야기하자고 한다. 다른 참가자의 이야기는 말하지 않는다 |

관계 패널은 공간 테이블에서 각자 자기 관계만 본다. 기존에 만들어진 그룹 방(공간이 아닌 방)은 지금처럼 관계가 바뀌지 않는다.

**배포 관련 수정**: `api/lounge-interaction.ts`는 Vercel에서 번들 없이 Node ESM으로 실행된다(2026-10-05 확장자 없는 import로 500 장애가 있었다). 이 함수가 관계 엔진을 쓰게 되어 `src/lib/relationship`의 상대 import에 `.js`를 붙였고, 배포 형태를 흉내 내는 테스트가 관계 모듈까지 함께 불러오도록 넓혔다.

**검증**: 공간 SQL 검사(첫 테이블, 자리 있으면 새 테이블 불가, 고른 테이블 앉기, 7번째 거절, 대기 순서와 대기자 우선, 오래 확인하지 않은 대기자 제외, 모두 찼을 때 새 테이블, 그룹 관계 저장과 장기 기억 차단, 다른 캐릭터·자리에 없는 사람 거절, 대화 보호 검토의 그룹 표시, 솔로, 기존 방, 재실행), 기존 SQL 검사 6개, 라운지 테스트, 배포 형태 테스트, 빌드. 홈·공간 페이지(자리 있음·아무도 없음·가득 참·대기 중)를 데스크톱과 390px에서 확인했다. 실제 여러 사람과의 음성, 그룹 관계 분류 품질은 배포 뒤 확인이 필요하다.

## 8. 홈 개편: 인물 카드와 상세 창 (2026-10-09)

- **홈**: 소셜/솔로 탭, 히어로, 공간 카드를 없앴다. 캐릭터 8명을 위 4명·아래 4명 정사각 프로필 카드로 보여 주고(모바일 2열), 사진 위에 이름과 짧은 직업(`LoungeCharacter.job`), 카드 아래에 `소셜 대화 · N명`만 둔다.
- **상세 창**: 카드를 누르면 홈 위에 창이 뜬다(`/lounge?character=<id>`, 뒤로 가기·Esc·바깥 클릭으로 닫힘). 사진, 한 줄 소개, 성격, 지금 대화 중인 인원과 주제, 그리고 버튼 셋.
  - `입장`: 내 테이블 → 빈자리가 있는 테이블 중 사람이 가장 많은 곳 → 테이블이 없으면 첫 테이블을 연다. 모든 테이블이 차면 `새 테이블로 입장`이 된다.
  - `대기`: 모든 테이블이 찼을 때만 누를 수 있다. 기존 대기 줄과 배너를 그대로 쓴다.
  - `둘이서 대화`: 솔로 플레이(기존 `/solo` 경로).
  - `인물 소개 전체 보기`로 기존 인물 소개 페이지에 간다. 공간 페이지(`/lounge/spaces/:id`)는 대기 배너의 `보기` 등에서 계속 쓴다.
- **대화방 배경**: 공간의 풍경이 아니라 캐릭터의 배경 목록(`loungeHostThemes`)에서 고른다. 방 ID로 고르므로 같은 방의 모든 참가자가 같은 배경을 보고, 목록에 배경이 여럿이면 방마다 달라진다. 배경 이미지와 강조색·바탕색은 `loungeThemes` 데이터에서 인라인 CSS 변수로 넣는다(풍경별 CSS 규칙은 없앴다). 새 배경을 추가하려면 `loungeThemes`에 항목 하나와 캐릭터 목록에 ID 하나를 넣으면 되고, DB는 바꾸지 않아도 된다.

## 9. 캐릭터 프롬프트: 인물 설정과 토큰 절약 (2026-10-09)

- 캐릭터는 AI·호스트·도우미가 아니라 이름과 직업, 과거가 있는 인물로 말한다(`loungeCharacterRules`). 진지하게 "AI냐"고 물을 때만 가상의 인물임을 한 문장으로 밝힌다.
- 인물 정보 전체(이름·나이·직업·살아온 이야기·성격·습관, 약 700~1,300자)를 항상 지시문 맨 앞에 둔다. 과거를 물을 때만 붙이는 방식은 패턴에 안 걸리는 질문에서 캐릭터가 얕아져서 되돌렸다.
- 지시문 순서: 고정 내용(프로필, 규칙, 공통 규칙, 관계·기억 지시, 역할) → 바뀌는 내용(현재 인원, 첫 인사 여부). 제공자의 프롬프트 캐시가 긴 앞부분을 재사용하게 하려는 순서다.
- 주제 자료·영화 카드·분야별 규칙은 주제 소개나 자료가 있는 방에만 넣는다(공간 방은 대부분 해당 없음).
- 크기 측정(글자 수, 공간 방 기준, 인물 정보 전체 포함): 1:1 약 3,660, 그룹 약 5,230(이전 5,334 / 6,905).
- 응답마다 `[Lounge model] {inputTokens, cachedTokens, cachedPercent}`를 로그에 남긴다. 배포 후 `cachedPercent`가 낮으면 `prompt_cache_key` 추가를 검토한다.

## 10. 캐릭터 지식·경험 쌓기 (2026-10-09)

- **무엇**: 캐릭터별로 전문 지식(사실·노하우)과 겪은 일(1인칭 일화)을 쌓는다. 항목이 늘어도 대화마다 드는 비용은 거의 같다. 질문과 가까운 항목 3개(최대 8)만 골라 지시문 맨 끝에 붙이기 때문이다.
- **입력**: 슈퍼 관리자 화면 `/super-admin/lounge-knowledge`(슈퍼 관리자 화면의 `캐릭터 지식·경험 관리` 버튼). 캐릭터를 고르고 종류·제목·내용(2,000자까지)을 쓴다. 수정·사용 중지·삭제가 된다. 저장하면 다음 대화부터 반영되고 배포는 필요 없다.
- **저장**: `lounge_character_knowledge`(마이그레이션 `20261011000000_lounge_character_knowledge.sql`). 임베딩은 `text-embedding-3-small`의 256차원을 길이 1로 맞춰 `real[]`에 저장하고, 질문과의 유사도는 SQL의 내적(`match_lounge_character_knowledge`)으로 구한다. pgvector가 필요 없고 캐릭터당 수천 개까지는 빠르다. 그 이상이면 pgvector로 옮긴다.
- **권한**: 목록·저장·삭제는 `is_super_admin()`만, 대화용 조회는 서버 역할만 호출할 수 있다. 방문자는 테이블에 접근할 수 없다. 저장 API(`api/lounge-knowledge.ts`)는 임베딩 요청 전에 권한부터 확인한다.
- **대화**: 사람의 마지막 발언 2개(6자 이상)로 임베딩을 만들어 조회한다(`LOUNGE_KNOWLEDGE=off`로 끌 수 있다). 항목이 없는 캐릭터는 임베딩도 조회도 하지 않는다(항목 유무를 가볍게 확인해 60초 기억, `LOUNGE_KNOWLEDGE_CACHE_MS`로 조정). 인사처럼 질문이 없거나, 조회가 0.8초 안에 끝나지 않거나, 실패하면 지식 없이 바로 답하고 늦은 조회는 취소한다. 로그: `[Lounge knowledge] {host, found, ms, embedMs, dbMs, scores, note}`(`note`는 `timedOut` 또는 `failed`)와 `[Lounge knowledge wait] {waitedMs}`. 응답이 지식 때문에 실제로 기다린 시간은 `waitedMs`다(조회는 다른 컨텍스트를 읽는 동안 병렬로 돌기 때문에 `ms`보다 짧다).
- **실명·개인정보**: 저장할 때 이메일·전화번호·인터넷 주소·주민등록번호·카드 번호가 들어 있으면 막는다(`loungeKnowledgeSensitive`). 회사·인물 이름은 패턴으로 가릴 수 없어서, 입력 화면의 작성 규칙(일반화해서 쓰기)과 대화 지시(캐릭터가 실제 회사·브랜드·실존 인물·사건 이름과 개인정보를 먼저 말하지 않고 "한 회사", "어떤 의뢰인"처럼 일반화)가 맡는다. 이미 저장된 항목은 다시 검사하지 않는다.
- **전문 질문 규칙**: 직업 관련 질문에는 "모른다"·"AI라서"라고 하지 않고 전문가로서 구체적으로 답한다. 확실하지 않으면 인물다운 말로 한계를 밝히고, 개별 사안의 법률·의료·투자 판단은 일반 지식 수준에서만 말한다.
- **선택 규칙**(`20261012000000_lounge_knowledge_selection.sql`, 조회 함수 `pick_lounge_character_knowledge`가 DB 안에서 처리하고 기록까지 한 번에 한다):
  - 한 번에 **일화(겪은 일)는 최대 1개, 지식은 최대 2개**.
  - 일화는 질문과의 일치도가 0.35 이상일 때만(지식은 0.28). 이 모델은 점수가 낮게 나오는 편이라 처음 0.45/0.3에서 낮췄다. `LOUNGE_KNOWLEDGE_MIN_EXPERIENCE`·`LOUNGE_KNOWLEDGE_MIN_KNOWLEDGE`로 배포 없이 조정하고, 로그 `[Lounge knowledge] scores`(예: `e0.41`,`k0.33`)로 실제 점수를 보며 맞춘다. 점수를 보려면 잠시 두 값을 0.05로 낮춰 두면 가까운 항목이 모두 로그에 찍힌다.
  - **한 번 들려준 일화는 그 사람에게 다시 나오지 않는다(기한 없음).** 지금 같이 있는 사람(최대 20명) 중 **한 명이라도 아직 못 들은 사람이 있으면 그 일화를 말하고**, 모두가 들었으면 다시 말하지 않는다. 일부가 이미 들은 일화는 `retold`로 표시해 캐릭터가 핵심만 짧게 다시 말하게 한다. 기록은 새로 듣는 사람에게만 남긴다(항목당 사람당 한 줄, 지우지 않고 항목을 삭제하면 같이 삭제). 같이 있는 사람을 알 수 없을 때만 그 방에서 이미 나온 일화를 제외한다. 일화가 모두 소진되면 그 사람에게는 지식만 나오고, 새 일화를 추가하면 다시 들을 수 있다. 같은 방에서는 45초 안에 일화를 또 보여 주지 않는다.
  - 지시문에는 "일화는 필요한 부분만 한두 문장, 쓴 뒤에는 지금 상대의 상황으로 돌아와 질문으로 이어가고, 이미 들려준 일화는 반복하지 않고, 일화 속 수치는 근거로 쓰지 않는다"를 넣는다.
- **항목 구조**: 일화에는 교훈(300자), 경험의 종류(성공·실패·결정적 선택·인간관계 갈등·전문적인 사건), 태그(10개까지), 본문 2,000자 이내(지식과 같다. 일화는 한 번에 하나만 들어가므로 길어도 그 턴에만 비용이 늘고, 길게 써 둘수록 이어지는 질문에 일관되게 답한다). 지식에는 출처 메모, 기준 날짜, **시한성 표시**(표시하면 기준 날짜 필수). 임베딩에는 제목, 태그, 교훈, 본문이 이 순서로 들어간다(3,000자까지, 길면 본문 끝이 잘리고 교훈은 남는다). 관리자 목록에는 일화를 들은 사람 수(`times_shown`)가 보인다.
- **가상 경험과 현실 지식 분리**: 종류(`kind`)로 나누고, 시한성 지식은 대화에서 "기준 YYYY-MM, 지금과 다를 수 있음"(1년이 넘으면 "오래된 정보")이라고 밝히며 지금의 사실이나 투자·법률·의료 판단의 근거로 단정하지 않는다. 일화의 수치와 결과는 현실의 근거로 쓰지 않는다.
- **적용 순서**: SQL Editor에서 `20261011…`을 실행한 뒤 `20261012…`를 실행(첫 파일은 한 번만, 둘째는 여러 번 실행해도 안전. 둘째를 이미 실행했어도 다시 실행하면 새 규칙으로 바뀐다). 개발·배포 환경에 설정 확인
- **(이전) 적용 순서**: SQL Editor에서 마이그레이션 실행 → 서버에 `OPENAI_API_KEY`와 `SUPABASE_SERVICE_ROLE_KEY` 설정 확인 → 배포.
- **나중에**: 최신 정보가 필요한 질문에만 웹 검색을 붙이는 것, 여러 항목을 한 번에 가져오기.
